Java 27

A focused quality-and-security release: G1 is now the default everywhere (even small containers), compact object headers flip from opt-in to on-by-default, a brand-new post-quantum TLS 1.3 hybrid key exchange lands as final, and JFR data redaction keeps secrets out of production profiling files — while the long-running previews (lazy constants, primitive patterns, structured concurrency, PEM encodings) each advance another round with targeted API refinements.

1 · Language features

Lazy Constants Preview (3rd) JEP 531

What changed from Java 26 (JEP 526, 2nd preview):

  • isInitialized() removed — checking whether a lazy constant has been initialized was deemed an antipattern (forces callers to reason about initialization state, defeating the point of lazy encapsulation). Remove any such checks; just call get().
  • orElse() removed — same reasoning. If you need a fallback value, use a try/catch around get() or guard with your own flag.
  • Set.ofLazy(Set<K>, Function<K,V>) added — the lazy collection family now has all three: List.ofLazy, Map.ofLazy, and now Set.ofLazy. Each element of the backing set is computed lazily and cached on first access.
Java 26 — methods removed in 27
LazyConstant<Config> cfg = LazyConstant.of(this::load);

// these no longer exist in Java 27:
if (!cfg.isInitialized()) warmUp();
Config c = cfg.orElse(Config.defaults());
Java 27 — just call get()
LazyConstant<Config> cfg = LazyConstant.of(this::load);

// get() is the only access path; failure retries, success caches
Config c = cfg.get();

// new in 27: Set.ofLazy
Set<String> roles = Set.of("admin", "user", "guest");
Set<Permissions> perms =
    Set.ofLazy(roles, role -> loadPermissions(role));

The full LazyConstant contract (compute-once, retry on failure, identity equals, cycle detection) is unchanged — see the Java 26 page for the detailed examples.

Primitive types in patterns, instanceof & switch Preview (5th) JEP 532

Why it's still in preview: the exhaustiveness rules for primitive types in sealed-class switches and the interaction between primitive narrowing patterns and numeric promotion required additional spec work. No user-visible API changes from Java 26 — this is an internal-correctness round. The feature allows:

Before — manual cast + range check
Object o = sensor.readValue();
if (o instanceof Number n) {
  double d = n.doubleValue();
  if (d == (int) d) process((int) d);   // fits-in-int check by hand
  else processDouble(d);
}
After (preview, Java 27)
switch (sensor.readValue()) {
  case int i    -> process(i);        // only matches if value fits exactly in int
  case double d -> processDouble(d);
  case null     -> handleMissing();
  default       -> {}
}

Structured Concurrency Preview (7th) JEP 533

What changed from Java 26 (JEP 525, 6th preview):

  • New third type parameter R_X — StructuredTaskScope and Joiner gain a third type parameter encoding the exception type the Joiner.result() method declares, giving type-safe checked-exception propagation: StructuredTaskScope<T, R, X extends Throwable>.
  • open() factory method added — a new static factory StructuredTaskScope.open(Joiner<T,R,X>) replaces the old constructor-style entry point, making the intent clearer and enabling future non-blocking entry points.
  • awaitAll() removed — the built-in Joiner that waited for all subtasks and never threw was removed. Use awaitAllSuccessfulOrThrow() or a custom Joiner instead.
  • onTimeout() → timeout() — the Joiner hook for handling scope timeout is renamed from onTimeout to timeout.
Java 26 style
try (var scope = StructuredTaskScope.open(
        Joiner.allSuccessfulOrThrow())) {
  var f1 = scope.fork(this::fetchUser);
  var f2 = scope.fork(this::fetchOrders);
  scope.join();
  return new Result(f1.get(), f2.get());
}
Java 27 (7th preview)
// open() is the new entry point; Joiner type params now include exception type
try (var scope = StructuredTaskScope.open(
        Joiner.<Result, List<Result>, RuntimeException>allSuccessfulOrThrow())) {
  var f1 = scope.fork(this::fetchUser);
  var f2 = scope.fork(this::fetchOrders);
  scope.join();
  return new Result(f1.get(), f2.get());
}

See the structured concurrency deep-dive for the full Joiner API, custom Joiner examples, and structural confinement rules.

2 · New & updated APIs

Post-Quantum Hybrid Key Exchange for TLS 1.3 Final JEP 527

Why it matters: current TLS 1.3 key exchange (ECDHE) is secure against today's computers but would be broken by a sufficiently powerful quantum computer using Shor's algorithm. JEP 527 adds three hybrid key-exchange mechanisms that combine ML-KEM (NIST-standardized, formerly known as Kyber) with classical ECDHE — so a connection is protected even if either algorithm is broken, but not both. The new named groups:

Named groupComponentsDefault?
X25519MLKEM768X25519 + ML-KEM-768Yes — enabled by default
SecP256r1MLKEM768secp256r1 + ML-KEM-768No
SecP384r1MLKEM1024secp384r1 + ML-KEM-1024No

X25519MLKEM768 is inserted into the default TLS named-groups list ahead of the existing ECDHE groups, so any TLS 1.3 server that also supports it will automatically negotiate post-quantum-hybrid key exchange — no code change required for existing applications.

Before — ECDHE only
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2)
    .build();
// TLS handshake uses ECDHE — vulnerable to future quantum attack
After (Java 27) — hybrid by default
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2)
    .build();
// TLS handshake now uses X25519MLKEM768 when the server supports it —
// no code change needed; Java 27 negotiates the hybrid group automatically

// Explicit opt-in to stronger variant for high-security contexts:
SSLParameters params = new SSLParameters();
params.setNamedGroups(new String[]{"SecP384r1MLKEM1024", "X25519MLKEM768"});
SSLContext ctx = SSLContext.getInstance("TLS");
ctx.init(null, null, null);
SSLEngine engine = ctx.createSSLEngine();
engine.setSSLParameters(params);
Interoperability: if the remote server doesn't support ML-KEM, the TLS handshake falls back to the next named group in the preference list (a classical ECDHE group) — there is no connection failure. The hybrid upgrade is transparent and backward-compatible.

PEM Encodings of Cryptographic Objects Preview (3rd) JEP 538

What changed from Java 26 (JEP 524, 2nd preview): the PEMDecoder and PEMEncoder classes gained support for PKCS#8 v2.0 (OneAsymmetricKey) key format and certificate revocation lists (CRL). The API shape is unchanged — the same PEMEncoder.of() / PEMDecoder.of() entry points, same encodeToString() / decode() methods. PEM encodings are on track to be finalized in Java 28 (JEP 542 has already been integrated targeting JDK 28).

// 3rd preview — same API as Java 26, now supporting CRLs:
PEMDecoder dec = PEMDecoder.of();
X509CRL crl = dec.decode(Files.readString(Path.of("revoked.pem")), X509CRL.class);

PEMEncoder enc = PEMEncoder.of();
System.out.println(enc.encodeToString(crl));   // -----BEGIN X509 CRL-----  ...

3 · Tooling & observability

JFR In-Process Data Redaction Final JEP 536

Why it matters: JDK Flight Recorder is the go-to profiling tool for production JVMs, but some of its built-in events capture data you'd rather not leave in a .jfr file — command-line arguments, environment variable values, and system property values can all contain API keys, passwords, or internal path names. JEP 536 lets you declare which fields to redact before they are written to the recording, so the sensitive data never touches disk.

Three built-in redaction targets, controlled via the JFR configuration file or @Redact annotation:

TargetJFR event fieldRedacted to
System propertiesjdk.SystemPropertyRead#value*redacted*
Environment variablesjdk.EnvironmentVariable#value*redacted*
JVM argumentsjdk.JVMInformation#jvmArguments*redacted*
Before — system property value written verbatim
// JFR recording with jdk.SystemPropertyRead would capture:
// value = "jdbc:postgresql://prod-db:5432/mydb?user=admin&password=s3cr3t"
After (Java 27) — redacted before write
// jfr config (profile.jfc) — declarative redaction:
// <event name="jdk.SystemPropertyRead">
//   <field name="value" redact="true"/>
// </event>

// JFR recording now writes:
// value = "*redacted*"  — never hits disk in cleartext

// For custom events, use @Redact on the field:
@Name("com.example.DBConnect")
class DBConnectEvent extends Event {
  String host;
  @Redact String password;   // redacted in recording, not in code
}
Redaction is in-process and zero-copy — the value is replaced before the event is serialized, so the sensitive string never appears in any JFR chunk, even in an in-memory continuous recording. There is no runtime overhead on code paths that don't emit the redacted events.

Vector API 12th incubator JEP 537

The Vector API continues to incubate — still requires --add-modules jdk.incubator.vector. No API changes this round. Finalization is blocked on Project Valhalla value types, which the Vector API needs to avoid boxing overhead. No Valhalla JEPs appear in JDK 27; this is the 12th consecutive incubator round.

4 · JVM / performance

G1 as Default GC in All Environments Final JEP 523

Why it matters: since Java 9 (JEP 248), G1 has been the default GC on server-class machines. But the JVM's ergonomic rules defined "server-class" as requiring at least 2 CPUs and at least 1792 MB of physical memory — configurations below that threshold (single-core containers, microservices with small heap caps) silently fell back to the Serial GC. JEP 523 removes that fallback: G1 is now the default everywhere on all supported platforms.

EnvironmentDefault GC before Java 27Default GC in Java 27+
Multi-core, ≥ 1792 MB RAMG1G1 (unchanged)
Single-core containerSerialG1
Heap < 512 MB (constrained)SerialG1
All other casesSerialG1
Before — Serial chosen automatically in a small container
$ java -Xmx256m -XX:+PrintFlagsFinal -version | grep UseSerialGC
# bool UseSerialGC = true  {product} {ergonomic}   <-- JVM picked Serial
After (Java 27) — G1 everywhere
$ java -Xmx256m -XX:+PrintFlagsFinal -version | grep UseG1GC
# bool UseG1GC = true  {product} {ergonomic}   <-- G1 in every environment

# To opt back to Serial (e.g. smallest-possible footprint CLI tools):
$ java -Xmx256m -XX:+UseSerialGC MyTool
G1 has lower throughput than Serial for tiny, short-lived workloads (CLI tools that live under 1 second) due to concurrent refinement thread startup. For those, pass -XX:+UseSerialGC explicitly. For containerized services with any meaningful traffic, G1 is the right default — concurrent marking avoids the long full-GC pauses Serial can produce as the live set grows.

Compact Object Headers by Default Final JEP 534

Why it matters: every Java object on a 64-bit JVM carries a header containing the mark word (8 bytes — hash code, lock state, GC age) and the class pointer (8 bytes uncompressed, or 4 bytes with compressed class pointers) — a minimum of 12–16 bytes per object before any fields. JEP 519 introduced an experimental Compact Object Header (Java 25) that squeezes both into a single 64-bit (8-byte) word by encoding the class pointer into spare bits of the mark word. JEP 534 flips this from opt-in (-XX:+UseCompactObjectHeaders) to on by default.

Standard header (pre-Java 27)Compact header (Java 27+)
Size16 bytes8 bytes
Mark word8 bytesMerged into single 64-bit word
Class pointer4–8 bytes (compressed or not)Encoded in spare bits of the mark word
Heap saving—Up to 10–20% for object-heavy workloads
Java 26 — 16-byte header, opt-in compact
$ java -jar agent.jar TargetApp   # standard 16-byte headers
$ java -XX:+UseCompactObjectHeaders -jar agent.jar TargetApp  # 8-byte, opt-in
Java 27 — 8-byte header by default
$ java -jar agent.jar TargetApp   # compact 8-byte headers by default

# To restore the 16-byte layout (for native tooling that hard-codes the size):
$ java -XX:-UseCompactObjectHeaders -jar agent.jar TargetApp
Tooling impact: native agents, JVMTI tools, and off-heap serializers that directly read the object header (e.g. to locate the class pointer at a fixed byte offset) must be updated. Instrumentation.getObjectSize() and sun.misc.Unsafe.objectFieldOffset() return correct values for compact headers and should be used instead of hard-coded offsets. Libraries known to hard-code header offsets: older versions of Kryo, some JVM profiling agents, some memory-layout inspection utilities.

5 · Summary cheat-sheet

Java 27 in one glance

  • G1 is now the default GC everywhere JEP 523: Serial is no longer auto-selected in constrained environments. Use -XX:+UseSerialGC explicitly for tiny CLI tools.
  • Compact object headers on by default JEP 534: every object header shrinks from 16 to 8 bytes. Native agents and tools that hard-code the old header size must be updated. Opt out with -XX:-UseCompactObjectHeaders.
  • Post-quantum TLS 1.3 JEP 527: X25519MLKEM768 (ML-KEM + ECDHE hybrid) is the new default named group — active automatically when the server supports it, no code change needed. Falls back to classical ECDHE if not supported.
  • JFR data redaction JEP 536: system properties, env vars, and JVM arguments can be redacted in JFR recordings before they hit disk. Use @Redact on custom event fields. No overhead on paths that don't emit the event.
  • Lazy Constants — 3rd preview JEP 531: isInitialized() and orElse() removed. Set.ofLazy() added (all three lazy collection types now exist). No other changes.
  • Structured Concurrency — 7th preview JEP 533: StructuredTaskScope and Joiner gain third type parameter for exception type; awaitAll() removed; onTimeout() renamed to timeout(); new open() factory.
  • Primitive patterns — 5th preview JEP 532: spec correctness fixes for exhaustiveness with primitives; no user-visible API changes.
  • PEM Encodings — 3rd preview JEP 538: gains PKCS#8 v2.0 and CRL support. On track to be final in Java 28.
  • Vector API — 12th incubator JEP 537: still requires --add-modules jdk.incubator.vector. Finalization awaits Project Valhalla. No API changes.
