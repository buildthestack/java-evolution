1 · How does HashMap work internally in Java 8+?

HashMap stores entries in an array of buckets, sized by its capacity (default 16) and grown based on its load factor (default 0.75) — per the javadoc, "when the number of entries in the hash table exceeds the product of the load factor and the current capacity, the hash table is rehashed" so it ends up with roughly twice the buckets. A key's bucket is chosen from its hashCode(). Within a bucket, colliding entries are chained; the javadoc itself notes that "when keys are Comparable, this class may use comparison order among keys to help break ties." Concretely (per the JDK's own HashMap source), since Java 8 a bucket whose chain grows past 8 entries — in a table with at least 64 buckets — is converted from a linked list into a balanced red-black tree, turning worst-case lookup in that bucket from O(n) into O(log n); it converts back to a list if the chain shrinks below 6.

Source: java.util.HashMap javadoc

2 · What happens when two keys have the same hash code?

A shared hash code just means two keys land in the same bucket — it does not mean the keys are equal. HashMap resolves this by storing every colliding entry in that bucket's chain (or tree, once it's long enough — see above) and calling equals() to tell the keys apart on get/put/remove. This is exactly why the Object.hashCode() contract only requires that "if two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result" — the reverse is explicitly not required: unequal objects producing the same hash code is legal, just something that "may improve the performance of hash tables" to avoid.

Source: Object.hashCode() javadoc · java.util.HashMap javadoc

3 · What happens when an object becomes eligible for Garbage Collection?

The java.lang.ref package javadoc defines a precise reachability ladder, and an object becomes GC-eligible when it drops off the bottom of it. An object is strongly reachable if reachable without going through any Reference object; softly/weakly reachable if only reachable by traversing a SoftReference/WeakReference; and finally, per the spec, "an object is unreachable, and therefore eligible for reclamation, when it is not reachable in any of the above ways." In practice: once no chain of strong references from a GC root reaches an object, it's eligible — the collector is free to reclaim it (after processing any weak/soft/phantom references pointing to it).

Source: java.lang.ref package javadoc

4 · What causes OutOfMemoryError vs StackOverflowError?

Both are subclasses of VirtualMachineError but signal opposite kinds of exhaustion. Per its javadoc, OutOfMemoryError is "thrown when the Java Virtual Machine cannot allocate an object because it is out of memory, and no more memory could be made available by the garbage collector" — the heap (or metaspace) is full. StackOverflowError, per its javadoc, is "thrown when a stack overflow occurs because an application recurses too deeply" — one thread's call stack ran out of space, almost always from unbounded or infinite recursion, independent of how much heap is free.

Source: OutOfMemoryError javadoc · StackOverflowError javadoc

5 · How does the JVM ClassLoader work?

ClassLoader uses a delegation model: per its javadoc, "each instance of ClassLoader has an associated parent class loader," and "when requested to find a class or resource, a ClassLoader instance will usually delegate the search... to its parent class loader before attempting to find the class or resource itself." The JDK has three built-in loaders forming a chain — the bootstrap loader (loads core java.base classes, has no parent), the platform loader (other JDK/Java SE classes), and the system/application loader (the application classpath). Concretely, loadClass first calls findLoadedClass to check a cache, then delegates to the parent, and only if the parent can't find it does it call findClass itself — which is why a class you define can never shadow one already loaded by an ancestor.

Source: java.lang.ClassLoader javadoc

6 · What is the difference between String, StringBuilder, and StringBuffer?

All three represent character sequences, but differ in mutability and thread safety. Per its javadoc, String is immutable: "strings are constant; their values cannot be changed after they are created... because String objects are immutable they can be shared." StringBuffer and StringBuilder are both mutable, but StringBuffer is, per its own javadoc, "a thread-safe, mutable sequence of characters" whose "methods are synchronized where necessary." StringBuilder, added in Java 5, is explicitly the unsynchronized alternative — its javadoc says it "provides an API compatible with StringBuffer, but with no guarantee of synchronization," and recommends it "be used in preference to StringBuffer as it will be faster under most implementations" whenever the buffer is only touched by one thread.

Source: String javadoc · StringBuilder javadoc

7 · What are Weak, Soft, and Phantom References?

These are the three "weaker than strong" reference types in java.lang.ref, ordered from least to most aggressively collected. Per the package javadoc: soft references "are for implementing memory-sensitive caches" — the JVM tries to hold onto softly-reachable objects and generally only clears them right before it would otherwise throw OutOfMemoryError. Weak references "are for implementing canonicalizing mappings that do not prevent their keys (or values) from being reclaimed" — cleared as soon as an object is only weakly reachable, no memory pressure needed (this is what backs WeakHashMap). Phantom references "are for scheduling post-mortem cleanup actions" — the referent is already finalized and unreachable through normal means, so get() always returns null; a phantom reference is only useful paired with a ReferenceQueue, which is how the program is notified to run cleanup after the object is really gone.

Source: java.lang.ref package javadoc
