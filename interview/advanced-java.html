1 · How does ConcurrentHashMap achieve thread safety?

ConcurrentHashMap's own javadoc states it plainly: "even though all operations are thread-safe, retrieval operations do not entail locking, and there is not any support for locking the entire table." Reads (get) never block and can overlap with writes — an update for a key has a happens-before relationship with any later read that observes it, so a reader never sees a torn value, only either the old or the fully-written new one. Since Java 8 this is implemented with per-bin synchronization (a CAS to install the first node in an empty bin, a lock on just that bin's head node for everything else) instead of Java 7's fixed 16-segment locking, plus the same treeification as HashMap for long bins — so contention is scoped to individual buckets, not the whole map.

Source: java.util.concurrent.ConcurrentHashMap javadoc

2 · What is the difference between volatile, synchronized, and AtomicInteger?

All three solve visibility/atomicity, but at different scopes. volatile only guarantees visibility and ordering — the JLS defines it precisely: "a write to a volatile field happens-before every subsequent read of that field" — but a compound action like count++ on a volatile field is still not atomic (it's a read, then a separate write). synchronized adds mutual exclusion on top of visibility: only one thread executes the block at a time, and "an unlock on a monitor happens-before every subsequent lock on that monitor," so it can protect an arbitrarily large critical section, at the cost of threads blocking. AtomicInteger gets both visibility and atomicity for a single variable without blocking, using lock-free compare-and-swap (per its javadoc, built on VarHandle) — ideal for counters, but it doesn't extend to multi-variable invariants the way a synchronized block can.

Source: JLS §17.4, Memory Model · AtomicInteger javadoc

3 · How does the Java Memory Model work?

The Java Memory Model (JLS Chapter 17.4) defines when a write by one thread is guaranteed to be visible to a read by another, through a relation called happens-before: "If one action happens-before another, then the first is visible to and ordered before the second." Without an explicit happens-before edge between two threads, the compiler, JIT, and CPU are all free to reorder or cache operations, so one thread may never observe another's write — this is what makes naively-shared mutable state buggy. The JLS builds happens-before from a few composable rules: program order within one thread, a volatile write happens-before every later read of that field, a monitor unlock happens-before the next lock on that same monitor, a thread start happens-before anything in that thread, and the whole relation is transitive. synchronized, volatile, and the java.util.concurrent classes are all built on top of these same rules.

Source: JLS §17.4.5, Happens-before Order

4 · How would you identify and fix a memory leak in Java?

Oracle's troubleshooting guide defines a memory leak plainly: "an application unintentionally holds references to Java objects or classes, preventing them from being garbage collected," showing up as "the live set increases over time after the application has reached a stable state and is under a stable load." Identify it by watching the live set (heap used right after a full GC) trend upward with JConsole or JDK Mission Control; once confirmed, take a heap dump — jcmd <pid> GC.heap_dump filename=heap.hprof (or automatically on failure with -XX:+HeapDumpOnOutOfMemoryError) — and load it into JDK Mission Control or Eclipse MAT to find the dominant retained-object path back to a GC root.

The fix is almost always one of: a static collection or cache that's never trimmed, listeners/callbacks registered but never unregistered, or a ThreadLocal never removed on a pooled thread (see the next question) — the dump's reference-chain view tells you which.

Source: Troubleshoot Memory Leaks, Java Troubleshooting Guide

5 · What problems can ThreadLocal cause in a thread pool?

ThreadLocal's own javadoc is the whole answer: "each thread holds an implicit reference to its copy of a thread-local variable as long as the thread is alive and the ThreadLocal instance is accessible; after a thread goes away, all of its copies... are subject to garbage collection." A pool thread never "goes away" between tasks — it's reused — so a value one task sets and forgets to clear is still sitting there, visible to the next unrelated task the pool runs on that same thread. That causes two distinct bugs at once: a slow memory leak (large values pinned for the thread's entire lifetime) and stale/cross-task data leakage (task B silently reads task A's leftover value). The fix the javadoc points at directly is calling remove() — typically in a finally block around the task — rather than relying on it being overwritten.

Source: java.lang.ThreadLocal javadoc

6 · How does CompletableFuture work internally?

CompletableFuture is a push-based, callback-driven CompletionStage: chaining methods like thenApply/thenAccept/thenCompose register a dependent action that fires automatically the moment the stage it depends on completes — no polling. Per the javadoc, for the non-Async methods "actions supplied for dependent completions... may be performed by the thread that completes the current CompletableFuture, or by any other caller of a completion method" — i.e. there's no dedicated worker, whichever thread happens to finish the upstream stage (or later attaches the callback, if it's already done) just runs it inline. The *Async variants opt out of that: "all async methods without an explicit Executor argument... are performed using ForkJoinPool.commonPool()," or a supplied Executor if you pass one.

That default matters in practice: the common pool is shared JVM-wide, so submitting a blocking or long-running task to it via a plain supplyAsync can starve unrelated async work elsewhere in the same JVM — the usual fix is passing a dedicated Executor for anything that blocks.

Source: java.util.concurrent.CompletableFuture javadoc

7 · What is ForkJoinPool and how does work-stealing work?

ForkJoinPool's javadoc names the mechanism directly: it "differs from other kinds of ExecutorService mainly by virtue of employing work-stealing: all threads in the pool attempt to find and execute tasks submitted to the pool and/or created by other active tasks (eventually blocking waiting for work if none exist)." Each worker thread owns its own double-ended queue; it pushes and pops its own newly-forked subtasks from one end (LIFO, so it works depth-first on the task it just created — good cache locality), while idle workers with nothing left steal from the other end of a busy worker's deque (FIFO), which minimizes contention since a worker's own end and the "stolen from" end are almost always different. That design, per the javadoc, "enables efficient processing when most tasks spawn other subtasks... as well as when many small tasks are submitted to the pool from external clients" — exactly the divide-and-conquer shape RecursiveTask/RecursiveAction and parallel streams use it for.

Source: java.util.concurrent.ForkJoinPool javadoc

8 · How would you detect and troubleshoot a deadlock?

Programmatically, ThreadMXBean has two purpose-built methods: findMonitorDeadlockedThreads() finds cycles where each thread "owns one monitor while trying to obtain another monitor already held by another... thread in a cycle" (plain synchronized deadlocks only), while findDeadlockedThreads() covers the wider case — cycles over "object monitors or ownable synchronizers," so it also catches deadlocks built from java.util.concurrent.locks.Locks. Operationally, the fastest path is a thread dump — jstack <pid> "attaches to the specified process and prints the stack traces of all threads," and automatically calls out any deadlock it finds, listing exactly which thread holds which lock while waiting for which other thread's lock.

Once you see the cycle, the fix is structural: enforce one global, consistent lock-acquisition order everywhere, or replace nested synchronized with tryLock(timeout) so a thread backs off instead of blocking forever.

Source: java.lang.management.ThreadMXBean javadoc · jstack, Java Troubleshooting Guide

9 · What happens when you create too many threads in a Java application?

Thread's own javadoc draws the line clearly: platform threads "are typically mapped 1:1 to kernel threads scheduled by the operating system," "will usually have a large stack and other resources that are maintained by the operating system," and — in the javadoc's own words — "may be a limited resource." Each one costs real native memory (a fixed-size stack, default around 512KB–1MB, controlled by -Xss) plus an entry in the OS's thread table; push past what the OS/JVM combination allows and you get OutOfMemoryError: unable to create native thread, often well before that ever-growing context-switching overhead alone tanks throughput. The javadoc's own recommended fix for high-concurrency, I/O-bound workloads is virtual threads: "a single Java virtual machine may support millions of virtual threads," at the cost that they're explicitly "not intended for long running CPU intensive operations."

Source: java.lang.Thread javadoc

10 · What is false sharing and how can it affect performance?

False sharing is a CPU cache-coherence effect, not something the JLS or any Java API defines — it happens when two unrelated variables written by different threads happen to land on the same CPU cache line, so an update from one core invalidates that whole line for every other core, forcing expensive cross-core cache traffic even though the threads never touch each other's actual data. The JDK's own (internal) answer is JEP 142's @Contended annotation, added in Java 8: applied to a field, the JVM pads memory around it so it lands alone on its own cache line. It isn't a supported public API (it targets JDK-internal classes and needs -XX:-RestrictContended to use elsewhere), but its effect is visible in the standard library: LongAdder's javadoc describes exactly this trade-off in user-facing terms — "when updates... are contended across threads, the set of variables may grow dynamically to reduce contention" — striping a hot counter across multiple padded cells specifically so concurrent writers land on different cache lines instead of fighting over one.

Source: java.util.concurrent.atomic.LongAdder javadoc

11 · How would you investigate high GC pauses in production?

Start with logging: Oracle's GC Tuning Guide says "a good start is to use the -Xlog:gc*=debug option," which gives "a detailed overview during and outside the pauses about garbage collection activity... including the type of collection and a breakdown of time spent in particular phases of the pause." Narrower tags dig further — gc+cpu=info shows the user/system/real time split per pause (useful for telling GC-bound from OS-scheduling-bound stalls), gc+heap=info shows region occupancy. For always-on production monitoring with near-zero overhead, JFR is the better fit than continuous -Xlog: it can run permanently and its recordings capture GC pause events (and, for leak-adjacent pauses, OldObjectSample) for later analysis in JDK Mission Control, without needing to reproduce the issue on demand.

If pauses are simply too long relative to your latency budget, the guide's own tuning knob is -XX:MaxGCPauseMillis — a goal G1 tries to hit by sizing regions and picking how much to collect per cycle, not a hard cap, so setting it unrealistically low just causes more frequent, smaller pauses instead.

Source: Garbage-First Garbage Collector Tuning, Java 25
