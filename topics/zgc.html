ZGC — The Z Garbage Collector Java 11

ZGC is the JVM's answer to one question: what if a garbage collector's pause times simply didn't grow with heap size — not at 1GB, not at 1TB? It gets there by doing almost everything concurrently, alongside your running application threads, and by hiding a small amount of GC bookkeeping directly inside object references themselves. This page goes from "what is it" to the exact bits in a pointer, using real output captured on a JDK 25 install, cross-checked against the OpenJDK JEPs, the ZGC wiki, Oracle's GC Tuning Guide, and dev.java.

The problem it solves Even G1 — the default collector since Java 9 — still stops every application thread for marking and compaction work that scales roughly with how much live data there is. On a small heap that's fine; on a 32GB+ heap serving low-latency traffic, that pause becomes visible to users. ZGC's entire design is built around one constraint: no pause may be proportional to heap size or live-set size — verified later on this page with a real 37ms-vs-0.009ms head-to-head against G1 on an identical workload.

1 · What ZGC Is, and Why It Exists

ZGC (the Z Garbage Collector — the letter isn't an acronym for anything) is a concurrent, region-based, compacting garbage collector built by Oracle and merged into OpenJDK as JEP 333 in JDK 11. Its one design goal, stated in its own JEP: keep every stop-the-world pause "not exceed 10ms" (an early target it has since blown well past, in the good direction — verified pauses below are sub-millisecond) and keep that pause time independent of heap size, live-set size, and root-set size, so a 100MB heap and a 10TB heap see the same worst-case pause.

It gets there with a technique borrowed from research garbage collectors: colored pointers — a handful of otherwise-idle bits inside every 64-bit object reference are used to store GC metadata directly in the pointer. Reading a reference runs through a tiny piece of injected code called a load barrier that checks those bits and, if the object has moved or hasn't been processed yet, fixes the pointer right there, in the reading thread, before handing back a valid reference. No thread ever needs a global pause to "catch up" — each thread heals the pointers it actually touches, exactly when it touches them.

This page covers two genuinely different ZGC architectures that both answer to -XX:+UseZGC, because the implementation was substantially rewritten mid-life: the original single-generation design (JDK 11–20) and Generational ZGC (JDK 21+, the default since JDK 23, the only mode since JDK 24 — i.e. what JDK 25/26 actually run). §4 and §5 cover each in turn, clearly labeled, because a lot of ZGC material online (including a PDF I cross-checked while writing this) describes the original architecture as if it were still current.

3 · The Core Idea: Region-Based Heap, Concurrent Everything

Both ZGC eras share the same foundational structure, which is what actually delivers the pause-time guarantee — the colored-pointer machinery in §4/§5 is how ZGC gets away with doing all this concurrently, not the source of the low pauses by itself.

PieceWhat it is
RegionsThe heap is divided into regions of three size classes — per dev.java's own architecture reference: Small (2MB, for objects ≤256KB), Medium (4–32MB, scales with max heap size, disabled below a 128MB max heap), and Large (sized in 2MB increments to fit one humongous object). Every GC cycle works region by region, never "the whole heap" at once.
Concurrent markingFinding which objects are still alive happens while the application keeps running — only tiny bracketing pauses (§7) mark the very start/end of the phase.
Concurrent relocationCompacting live objects out of mostly-garbage regions into fresh ones also happens concurrently — this is the hard part, and it's what colored pointers and load barriers exist to make safe (§4/§5).
Only 2–3 brief STW pauses per cycleJust enough to snapshot GC roots (thread stacks, etc.) at the start of marking and the start of relocation — their cost is proportional to the root set (a small, roughly-constant number of references), never to live-set or heap size.

4 · How the Original ZGC Worked (JDK 11–20) — Colored Pointers & Multi-Mapping

This architecture shipped from JDK 11 through JDK 20, was deprecated once generational ZGC became the default in JDK 23, and was deleted entirely in JDK 24 (JEP 490) — it no longer exists in the JDK you're most likely running. It's covered here because it's genuinely excellent, widely-referenced design, and because generational ZGC (§5) is easiest to understand as "the same problem, solved differently."

4.1 · The colored pointer

A 64-bit object reference has far more bits than any real heap needs for addressing. Per dev.java's architecture deep-dive, the original ZGC reserves the top 20 bits of every reference for metadata, leaving 44 bits for the actual object address — exactly 244 bytes, or 16TB, the maximum heap size this scheme supports. Only 4 of those 20 reserved bits were actually used (the other 16 sat in reserve for future use):

BitMeaning
Finalizable"Indicates if the object is only reachable through a finalizer" — a narrow, rarely-hit case.
RemappedIndicates the pointer is known not to point into the current relocation set — i.e. it's already up to date.
Marked0 / Marked1Indicates the object is known to be marked live by the current GC cycle. ZGC alternates which of the two counts as "good" between cycles, so it never needs to bulk-clear a mark bitmap.

Layout, top bits to bottom:

bits 63 .. 44 (20 bits)   bits 43 .. 0 (44 bits)
[ unused(16) F R M1 M0 ]  [        object address        ]
  reserved metadata          -> 2^44 bytes = 16 TB max heap

4.2 · The load barrier — self-healing pointers

A load barrier is a small piece of code the JIT injects at every point application code reads an object reference off the heap — anywhere you write something like o = obj.field. At any moment, ZGC has declared exactly one color "good" for the current phase (e.g. "Marked0 is good right now"). The barrier's whole job is one fast comparison:

if (pointerColor != currentGoodColor) {
  // stale or unmarked -- heal it right here, on this thread
  o = relocateAndHealPointer(o);
}
// o is now guaranteed valid and correctly colored

If the color already matches, the thread passes through with a single cheap check and zero other overhead. If it doesn't, the thread (not a GC thread) looks up the object's current address in ZGC's forwarding table, patches the pointer in place, and continues — the healing cost lands only on threads that actually touch a stale reference, never as a global pause.

4.3 · Multi-mapping — teaching ordinary hardware to tolerate colored bits

Colored bits baked into an address would make plain hardware dereference garbage — the CPU doesn't know to strip them, and stripping them in software on every access would be far too slow. ZGC's original fix, per dev.java: "the physical location of an object is mapped to three views in virtual memory, corresponding to each of the pointer's potential 'colors'" — a Marked0 view, a Marked1 view, and a Remapped view, all backed by the exact same physical RAM via the OS's mmap (or the macOS/Windows equivalents added by JEP 364/365). Whichever view a pointer's color bits happen to route it through, it lands on the same physical page — nothing needs cleaning up in software, and the "masking" problem disappears because the hardware was never shown a raw, un-mapped colored address in the first place.

This mechanism is why the original ZGC needed a huge virtual address-space reservation regardless of how much heap was actually used — three views of up to 16TB each. It's also the direct cause of the memory-reporting confusion covered in §6.

5 · Generational ZGC (JDK 21+) — What Changed, and What You Run Today

JEP 439 rebuilt large parts of ZGC around one long-standing GC observation — the "weak generational hypothesis": most objects die young. Splitting the heap into young and old generations lets ZGC collect just the young generation, far more often and far more cheaply, without ever touching the (usually much larger) old generation. Doing that safely needed two real architectural changes, both confirmed by fetching JEP 439 directly:

5.1 · The bit layout flipped

This directly contradicts the original layout in §4.1 — verified by fetching JEP 439's own text: "The colored pointer layout used by Generational ZGC puts the metadata in the low-order bits of the pointer and the object address in the high-order bits." Metadata moved from the top of the pointer to the bottom; the object address moved from the bottom to the top. If you've read an explainer describing colored bits as living in the high-order bits of the pointer, it's describing the pre-JDK-21 design from §4, not what -XX:+UseZGC gives you on JDK 21 and later.

5.2 · Multi-mapping is gone — replaced by explicit barrier code

Per the JEP: "Non-generational ZGC uses multi-mapped memory to reduce the overhead of load barriers. Generational ZGC instead uses explicit code in the load and store barriers." Instead of routing a stale pointer through a second virtual-memory view to land on the right physical page, the barrier itself now contains the logic to detect and fix a bad pointer directly — no OS-level multi-mapping trick, and (per the JEP) one deliberate side benefit: "it makes it easier to measure the amount of memory used for the heap" — a direct fix for the RSS confusion covered next in §6.

5.3 · The new problem: cross-generation pointers, and the store barrier

To collect only the young generation safely, ZGC needs to know which old-generation objects hold references into it — otherwise every young collection would have to scan the entire old generation just to find its roots, defeating the entire point. The fix is a second barrier that runs on writes, not reads:

Load barrierStore barrier
Runs ona read — x = obj.fielda write — obj.field = y
JobSelf-heals a moved or stale pointer the instant it's touchedNotices when an old-generation object starts pointing at a young one
Cost profileRuns constantly — one cheap color-bit comparisonRuns on writes only — keeps young-only collections fast by avoiding an old-generation scan

Per JEP 439, verbatim: "Store barriers add entries to the remembered set. Whenever a reference is stored into an object field, it is considered to potentially contain an old-to-young generation pointer." The remembered set itself is implemented as double-buffered bitmaps — the JEP again: "Each old-generation region has a pair of remembered-set bitmaps. One of the bitmaps is active and populated by application threads." Come collection time, a young-only cycle only has to consult those small per-region bitmaps, never the whole old generation.

5.4 · Both barriers, on one ordinary method

An everyday method that writes a field and reads it straight back exercises both barriers in sequence:

public void updateAndPrintProfile(User user, Profile newProfile) {
  user.profile = newProfile;                 // WRITE -> store barrier
  Profile activeProfile = user.profile;       // READ  -> load barrier
  System.out.println(activeProfile.getDetails());
}

Conceptually, what the JIT has woven in around it:

// ---- the write: store barrier ----
if (isOldGeneration(user) && isYoungGeneration(newProfile)) {
  addToRememberedSet(user);   // record this old->young link
}
user.profile = newProfile;

// ---- the read: load barrier ----
if (hasBadColor(user.profile)) {
  user.profile = relocateAndHealPointer(user.profile);   // stale, heal on the fly
}
Profile activeProfile = user.profile;
System.out.println(activeProfile.getDetails());
Every single field write and field read in a generational-ZGC-collected program passes through one of these two barriers. That they're each just one cheap comparison in the common case is exactly why ZGC's steady-state throughput overhead, while real (§10), is small enough to be practical for general server workloads.

6 · The "Tripled Memory" Illusion — Real History, Verified Fixed

A well-known ZGC gotcha: because the original architecture (§4.3) mapped every live object into three separate virtual-memory views, naive memory-reporting tools that summed up mapped regions could report a process using far more memory than it actually held. This was real and is exactly why JEP 439 lists "easier to measure heap memory" as a deliberate benefit of dropping multi-mapping.

I verified this is actually fixed on generational ZGC — ran a program holding ~300MB of genuinely live heap under -XX:+UseZGC -Xmx1g -Xms1g on this JDK 25 (macOS) install:

$ ps -o pid,rss,vsz -p <pid>
  PID    RSS      VSZ
92035 340160 454905456        # RSS ~332MB -- matches real usage, NOT tripled to ~900MB

$ vmmap <pid> | grep "Physical footprint"
Physical footprint:         309.9M   # also tracks real usage directly
Verified real finding: RSS and physical footprint both track actual memory use accurately on generational ZGC. Only VSZ (virtual size) is enormous — in this same run it was ~434GB for a 1GB max heap — because ZGC still reserves a huge virtual address range up front (see the 16x ratio in §9). That's expected and harmless: virtual address space costs nothing until it's actually backed by physical pages. The "tripled RSS" problem was real for pre-JDK-21 ZGC's multi-mapping; it does not reproduce on the generational architecture every JDK 25/26 install actually runs.

The default one-line-per-cycle view already shows the generation split — "Minor" for young-only cycles, "Major" for cycles that also touch the old generation:

$ java -XX:+UseZGC -Xlog:gc -Xmx256m -cp . ZTest
Verified real output — captured on this JDK 25 install, no flags beyond -XX:+UseZGC:

The first few cycles are always "Warmup" Major collections — ZGC hasn't gathered enough allocation statistics yet to know it can safely skip the old generation. Once it has data, cycles are triggered either by Allocation Rate (the normal, adaptive trigger) or by a fixed -XX:ZCollectionInterval if one is set (§9).

Adding gc,phases to the log selector reveals the individual pauses inside one cycle — this is the direct proof that ZGC's stop-the-world work is tiny and constant, not proportional to anything:

$ java -XX:+UseZGC -Xlog:gc,gc+phases -Xmx6g -cp . GcBench2

8 · Verified Benchmark — ZGC vs G1, Identical Workload

Same program, same JVM, same machine, same -Xmx6g — a ~3GB live set held in memory while ~10GB of garbage churns through it, deliberately large enough to make a copying collector's per-pause cost visible:

List<byte[]> live = new ArrayList<>();
for (int i = 0; i < 3000; i++) live.add(new byte[1_000_000]);   // ~3GB live set

Random r = new Random(42);
for (int i = 0; i < 20000; i++) {
  byte[] junk = new byte[500_000];                              // ~10GB total churn
  if (r.nextInt(500) == 0) live.set(r.nextInt(live.size()), new byte[1_000_000]);
}
$ java -XX:+UseG1GC -Xmx6g -Xlog:gc -cp . GcBench2
$ java -XX:+UseZGC  -Xmx6g -Xlog:gc,gc+phases -cp . GcBench2
Verified real output — worst single pause of the run, each collector, same workload: 
G1:  GC(15) Pause Remark                          3157M->3157M(5116M)   0.771ms
G1:  GC(20) Pause Remark                          3330M->3330M(5120M)   0.347ms
G1:  GC(23) Pause Young (Prepare Mixed)(Evac.)     5043M->3087M(5400M)   4.961ms
G1:  worst pause across the whole run:                                 37.350ms

ZGC: GC(1) Y: Pause Mark Start (Major)                                  0.009ms
ZGC: worst individual STW pause across the whole run:                   0.009ms

On identical work, G1's worst pause was 37.35ms; ZGC's worst pause was 0.009ms — roughly a 4,000× difference. That gap is the entire reason ZGC exists. It isn't free, though: in this same run ZGC finished its total work in somewhat more wall-clock time than G1 did (concurrent marking/relocation and constant barrier checks cost real CPU and throughput — see §10 for the honest trade-off framing dev.java itself uses).

10 · When to Reach for ZGC (and When Not To)

dev.java's own overview page is refreshingly direct about this, and it's worth quoting exactly: ZGC "was not designed... to be a general upgrade" over G1, Parallel, or Serial. It trades some CPU and memory overhead — the constant load/store barrier checks, plus the concurrent marking/ relocation threads competing for cores — for pause times that stay flat regardless of heap size.

Good fitWhy
Large heaps (tens of GB and up)Verified in §8: ZGC's pause doesn't grow with heap or live-set size; G1's does.
Latency-sensitive services (trading, real-time bidding, gaming backends)Sub- millisecond worst-case pauses matter more than squeezing out maximum throughput.
Systems with plenty of spare CPU coresConcurrent marking/relocation needs cores to run on without stealing them from the application.
Poor fitWhy
Single-core or CPU-constrained systemsdev.java's own guidance: ZGC "is not recommended... on systems with a single or very limited number of CPUs" — there's no spare core for concurrent work to hide on.
Small heaps, short-lived CLI tools, batch jobsThe fixed overhead (barrier checks, large virtual-memory reservation, warmup cycles) isn't worth paying when nobody's waiting on a pause anyway — Serial or Parallel wins here (see the JVM Memory & GC deep dive).
Pure throughput-maximizing batch/ETL workloadsParallel GC's simpler, fully-STW design generally gets more total work done per CPU-hour when nobody cares about individual pause length.

For what generational ZGC specifically improved over the old single-generation design, Oracle Java Developer Advocate Billy Korando's own numbers (published alongside the JEP 439 rollout) are concrete: roughly a 10% throughput improvement over single-generation ZGC on a JDK 17 baseline, an average per-request latency regression of only 2–3 microseconds, and P99 pause improving by 10–20% in their benchmark, remaining stable up to 275 concurrent clients.

12 · ZGC vs G1 vs Shenandoah

G1 and ZGC are both shipped by every OpenJDK build (Oracle-led). Shenandoah — included here because it's the collector most often compared to ZGC — is Red Hat's low-pause collector, built independently with a different mechanism; it's general Java-ecosystem knowledge rather than something Oracle/dev.java documents, so it's flagged as such below.

13 · Cheat Sheet

ZGC in one glance

  • What it is: a concurrent, region-based, compacting collector whose stop-the- world pauses stay flat regardless of heap or live-set size — verified 0.009ms worst pause vs G1's 37.35ms on an identical 6GB-heap workload (§8).
  • History: JEP 333 (Java 11, experimental, Linux-only) → JEP 364/365 (Java 14, macOS/Windows) → JEP 377 (Java 15, production everywhere) → JEP 439 (Java 21, generational, opt-in) → JEP 474 (Java 23, generational by default) → JEP 490 (Java 24, non-generational mode deleted — -XX:+UseZGC now always means generational).
  • Two different architectures answer to the same flag: pre-JDK-21 used high-order metadata bits + three-way multi-mapped virtual memory (§4); JDK 21+ flips metadata to the low-order bits, drops multi-mapping, and adds a store barrier + remembered sets for generations (§5). Content describing colored bits as "high-order" is describing the old, now-deleted design.
  • The "tripled RSS" gotcha was real, and is fixed: verified generational ZGC's RSS/physical-footprint tracks actual usage accurately; only virtual size (VSZ) balloons, by a verified constant ~16× the configured -Xmx (§6, §7).
  • Enable it: -XX:+UseZGC — no other flag needed on JDK 24+.
  • Watch it: -Xlog:gc (Minor/Major, one line per cycle) or -Xlog:gc,gc+phases (every individual Pause/Concurrent sub-phase, §7).
  • Not a free upgrade: per dev.java, "not designed to be a general upgrade" — skip it on single-core boxes or tiny short-lived processes; reach for it on large heaps with latency requirements and spare CPU (§10).
  • See also: the broader JVM Memory Model & GC deep dive for how ZGC fits alongside Serial, Parallel, G1, and Shenandoah.
