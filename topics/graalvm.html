GraalVM & Native Image

GraalVM compiles Java all the way down to a standalone native binary — no JVM needed at runtime. You get millisecond startup, a tiny memory footprint, and a single self-contained executable. This page explains how it works, how to build and run it, what the trade-offs are, and how it differs from the JDK's built-in AOT Cache.

~10 mstypical native image startup
50–80%less memory than a JVM app
no JVMneeded at runtime
closed-worldassumption — the key trade-off
The problem it solves Traditional Java needs a JVM to start up, warm up, and reach peak performance. For a command-line tool, a serverless function, or a microservice behind a load balancer, the JVM's warm-up latency and large memory footprint are a real cost. GraalVM Native Image eliminates both by compiling the entire application — including the JDK, framework, and your code — into a single native executable at build time.

1. What is GraalVM?

GraalVM is a high-performance JDK distribution maintained by Oracle. It contains everything a standard JDK has, plus two major extras:

  • The Graal JIT compiler — a drop-in replacement for C2 (the standard JVM's top-tier JIT), written in Java. It can produce tighter code for certain workloads. It was available as an experimental option in standard JDKs via JVMCI, but JVMCI is being removed in Java 27 (JEP 503), so this path is closing in the standard JDK.
  • Native Image — an AOT compiler that analyses your application statically and compiles everything into a standalone native executable. This is the main reason to use GraalVM today.

The three distributions you'll encounter:

DistributionWho makes itCostKey extras
GraalVM Community Edition (CE)Oracle / open sourceFree (GPLv2)Native Image, Graal JIT
Oracle GraalVM (formerly EE)OracleFree for production since 2023CE + PGO, G1 GC in native, better throughput
MandrelRed HatFreeCE without Graal JIT — only Native Image; designed for Quarkus

2. Two execution modes

Any Java program can run in either mode — the choice is made at launch time (JVM mode) or build time (native):

ModeHow you run itJIT at runtimeStartupPeak throughput
JVM mode java -jar app.jar Yes (Graal JIT) Normal JVM start (~1–5 s) High (JIT-optimised, may exceed C2)
Native Image ./app No (AOT only, no C2 or Graal JIT) Milliseconds (5–50 ms) Good (~70–85% of JVM; higher with PGO)

For long-running services like REST APIs, JVM mode eventually wins on throughput because the JIT can profile real traffic. For short-lived processes (CLI tools, serverless, sidecar containers), Native Image wins hands down.

4. Hello World — build & run

4.1 Write the Java source

// Hello.java
public class Hello {
    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : "World";
        System.out.println("Hello, " + name + "!");
        System.out.println("Running as native: " +
            (System.getProperty("org.graalvm.nativeimage.imagecode") != null));
    }
}

4.2 Compile with javac

javac Hello.java
# Produces Hello.class — a normal .class file

4.3 Build the native image

native-image Hello

4.4 Run it

# Run the native binary — no java command, no JVM
./hello
# Hello, World!
# Running as native: true

./hello GraalVM
# Hello, GraalVM!
# Running as native: true

# Compare startup time
time java Hello        # ~150–300 ms (JVM startup + class loading)
time ./hello           # ~5–15 ms (native, no JVM)

# Check the binary — it really is standalone
file hello
# hello: Mach-O 64-bit executable arm64   (macOS)
# hello: ELF 64-bit LSB executable, x86-64 (Linux)

ldd hello       # shows libc and libpthread only — no JVM libraries!
Build time is slow (15–60 seconds) — that's expected. Static analysis must trace every reachable class and method from the entry point. This happens once at build time, never at runtime.

5. Realistic example — file word-count CLI

A small CLI tool: reads a file, prints line count, word count, char count. Exactly the kind of thing that benefits enormously from instant startup. 

// Wc.java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class Wc {
    public static void main(String[] args) throws IOException {
        if (args.length == 0) {
            System.err.println("Usage: wc <file>");
            System.exit(1);
        }
        Path path = Path.of(args[0]);
        String content = Files.readString(path);
        String[] lines = content.split("\n");
        String[] words = content.trim().isEmpty()
            ? new String[0] : content.trim().split("\\s+");

        System.out.printf("%6d  %6d  %6d  %s%n",
            lines.length, words.length, content.length(), args[0]);
    }
}
# Build
javac Wc.java
native-image Wc

# Run
./wc Wc.java
#     18      82     578  Wc.java

# The native version starts in ~8 ms vs ~180 ms for `java Wc`
# For a script run 100 times a day that's 17 seconds saved daily

5.1 JAR-based build (more realistic)

6. How Native Image works

Native Image uses a points-to analysis (also called reachability analysis) to determine every class, method, and field that can possibly be reached from your main() at runtime. Only reachable code gets compiled. Everything else is discarded — this is what makes the binary small.

Build-time phaseWhat happens
InitializingLoads the classpath, finds the entry point
Performing analysisPoints-to analysis — finds all reachable code (slowest step)
Building universeBuilds type hierarchy for the reachable set
Parsing methodsConverts bytecode to an IR for compilation
Inlining methodsAggressive inlining (more than the JIT can safely do)
Compiling methodsGenerates machine code via LLVM-style backend
Creating imageLinks code + pre-initialised heap into one binary

Closed-world assumption

Because the analysis runs before you deploy, all code must be known at build time. You cannot load classes from a URL, add new JARs to the classpath at runtime, or do anything that requires knowing about code that wasn't there when native-image ran. This is the fundamental trade-off: power vs. dynamism.

Dynamic features — reflection, JNI, dynamic proxies, serialization — all violate the closed-world assumption unless you tell Native Image about them via configuration files (see the next section).

Pre-initialised heap

Static initialisers that run at build time have their results "snapshotted" into the binary's heap. When the native binary starts, those objects already exist — this is a major source of startup speed. You can control this with @TargetClass and RuntimeClassInitialization if you have initialisers that must run at runtime.

7. Reflection & dynamic features

Any feature that decides what to do at runtime — reflection, JNI, dynamic proxies, Java serialization, resource loading — is opaque to the static analysis. You must declare these explicitly so Native Image can include the required metadata in the binary.

7.1 Automatic detection — the Tracing Agent

The easiest way: run your application on the JVM with the tracing agent and let it record all dynamic accesses automatically. 

# Run the app with the agent — exercise ALL code paths (tests, integration tests)
java -agentlib:native-image-agent=config-output-dir=src/main/resources/META-INF/native-image \
     -jar app.jar

# The agent writes these files:
# META-INF/native-image/
#   reflect-config.json      ← reflection
#   proxy-config.json        ← dynamic proxies
#   resource-config.json     ← classpath resources
#   serialization-config.json ← Java serialization
#   jni-config.json          ← JNI

# Now build — native-image picks up these files automatically
native-image -jar app.jar

7.2 Manual reflect-config.json

// src/main/resources/META-INF/native-image/reflect-config.json
[
  {
    "name": "com.example.UserDto",
    "allDeclaredFields": true,
    "allDeclaredMethods": true,
    "allPublicConstructors": true
  },
  {
    "name": "com.example.OrderDto",
    "allDeclaredFields": true,
    "allDeclaredMethods": true,
    "allPublicConstructors": true
  }
]

7.3 Reachability metadata repository

GraalVM maintains a community-contributed registry of metadata for popular libraries (Jackson, Hibernate, Netty, etc.) at github.com/oracle/graalvm-reachability-metadata. Most build tool plugins add this automatically — you often don't need to write reflect-config.json for any mainstream library.

7.4 @RegisterForReflection (Quarkus / framework annotation)

// If using Quarkus or Micronaut, annotate your DTO instead of a JSON file
@io.quarkus.runtime.annotations.RegisterForReflection
public class UserDto {
    public String name;
    public int age;
}

9. Spring Boot native images

Spring Boot 3.x / Spring Framework 6.0 added first-class native image support via a built-in AOT engine. The short version: Spring does at build time everything it used to do at startup — condition evaluation, component scanning, proxy generation — and emits generated code and hint files that GraalVM's native-image consumes.

Quick start

# New project: tick "GraalVM Native Support" at start.spring.io
# Existing Maven project — add the native profile and plugin (see §8 Maven), then:

# Local binary (fastest iteration)
mvn -Pnative native:compile
./target/myapp                     # starts in ~80–150 ms

# OCI image via Buildpacks (production-ready container)
mvn spring-boot:build-image -Pnative
docker run myapp:latest

# Gradle
./gradlew nativeCompile
./build/native/nativeCompile/myapp

10. How the Spring AOT engine works

When you run mvn -Pnative native:compile, the build plugin first runs spring-boot:process-aot, which launches a special JVM process (not native-image yet) that does this:

  1. Partially starts the ApplicationContext — loads all @Configuration classes, evaluates every @Conditional, resolves all component scanning, detects all beans.
  2. Generates Java source code — instead of bean definitions that use reflection at runtime, it emits explicit factory classes: UserServiceBeanDefinitions.java, DataSourceAutoConfigurationBeanDefinitions.java, etc. At runtime the native binary calls these factory methods directly — no reflection, no scanning.
  3. Emits resource hint files — everything native-image needs to know about reflection, proxies, resources, and serialization:
    • reflect-config.json
    • proxy-config.json
    • resource-config.json
    • serialization-config.json
    These are written to target/spring-aot/main/resources/META-INF/native-image/ and picked up automatically by native-image.

After process-aot finishes, native-image compiles the application together with the generated sources, so the binary has no need for Spring's reflection-heavy initialisation logic at all. 

# Inspect what Spring generated (very useful for debugging)
ls target/spring-aot/main/
# sources/      ← generated Java: *BeanDefinitions.java, proxy classes, hint registrars
# resources/
#   META-INF/native-image/
#     reflect-config.json
#     proxy-config.json
#     resource-config.json
#     serialization-config.json

# Run only the AOT processing step (without native compilation) to check for errors early:
mvn spring-boot:process-aot
Reading target/spring-aot/main/sources/ is the best debugging tool when a bean or library isn't working in native. It shows exactly what Spring decided to generate — or failed to generate — for each bean.

11. Third-party & legacy library support

The closed-world assumption breaks most libraries that use reflection internally. Spring handles this through four layers applied in order — each layer covers more libraries automatically, with less work from you.

Layer 1 — GraalVM Shared Reachability Metadata Repository

This is the most powerful layer — it requires zero code changes from you.

Oracle hosts a community-driven repository at github.com/oracle/graalvm-reachability-metadata that contains pre-built reflect-config.json, proxy-config.json, resource-config.json, and serialization-config.json for hundreds of mainstream libraries that don't ship their own hints: PostgreSQL/MySQL JDBC drivers, Jackson, Hibernate, Netty, HikariCP, Caffeine, Mockito, Lombok, Bouncy Castle, and many more. Each library entry is versioned — the metadata for postgresql:42.6.0 is separate from postgresql:42.7.0 so you always get the right config for the exact version you're using.

How Spring Boot wires it automatically: when you run mvn -Pnative native:compile, the native-maven-plugin (or native-gradle-plugin) reads your dependency list, queries the metadata repository for each dependency, downloads the matching config files, and injects them into the native-image build — before your code is compiled to native. You never see the downloaded files; they are merged silently in the build working directory. 

<!-- pom.xml — metadataRepository is ON by default in native-maven-plugin 0.9.19+ -->
<plugin>
  <groupId>org.graalvm.buildtools</groupId>
  <artifactId>native-maven-plugin</artifactId>
  <version>0.10.3</version>
  <extensions>true</extensions>
  <configuration>
    <metadataRepository>
      <enabled>true</enabled>  <!-- already the default -->
    </metadataRepository>
  </configuration>
</plugin>
// build.gradle — same, enabled by default
graalvmNative {
    metadataRepository {
        enabled = true   // default; shown for clarity
    }
}

Checking coverage — which of your dependencies have metadata?

# Maven: list which dependencies were resolved from the metadata repository
mvn -Pnative native:compile -Dnative.verbose=true 2>&1 \
  | grep -i "metadata\|reachability"
# Lines like:
# [native] Found GraalVM reachability metadata for org.postgresql:postgresql:42.7.3

# Gradle:
./gradlew nativeCompile --info 2>&1 | grep -i "reachability"

# To see the full list of covered libraries in the repository:
# Browse: github.com/oracle/graalvm-reachability-metadata/tree/main/metadata
# Or use the GitHub search: site:github.com/oracle/graalvm-reachability-metadata <library-name>

A library is NOT in the repository — what happens?

The build doesn't fail. native-image simply won't have config for that library, so any reflection it does at runtime will throw a MissingReflectionRegistrationError (or silently return null for older libraries). This is when you move to Layers 2–5 below.

You can also contribute missing metadata back to the community repo via a pull request — the repository actively accepts contributions, and that benefits every project that uses the same library.

Layer 2 — Library ships a RuntimeHintsRegistrar

A library that is aware of native compilation can ship a registrar class that Spring calls during the AOT phase. Spring Boot's own starters all do this internally; well-maintained third-party libraries (e.g. MapStruct, Micrometer, Flyway) do too. 

// Inside the library (not your code) — registered via META-INF/spring SPI or @ImportRuntimeHints
public class JacksonRuntimeHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.reflection()
            .registerType(MyDto.class,
                MemberCategory.INVOKE_PUBLIC_CONSTRUCTORS,
                MemberCategory.INVOKE_PUBLIC_METHODS);
        hints.resources()
            .registerPattern("jackson-databind.properties");
    }
}

// Activated via SPI file:
// META-INF/spring/org.springframework.aot.hint.RuntimeHintsRegistrar
// com.example.JacksonRuntimeHints

Layer 3 — BeanRegistrationAotProcessor (framework-level, per-bean)

For libraries that do complex per-bean reflection (Spring Data repositories, Spring Security method security, Spring AOP advisors), there is a lower-level SPI that Spring calls once per matching bean during AOT processing. This is how Spring Data turns a interface UserRepository extends JpaRepository<User,Long> into generated proxy code at build time so no dynamic proxy is needed at runtime. 

// Spring Data ships one of these internally — shown here for understanding
public class RepositoryRegistrationAotProcessor
        implements BeanRegistrationAotProcessor {

    @Override
    public BeanRegistrationAotContribution processAheadOfTime(
            RegisteredBean registeredBean) {
        // Called once per @Repository bean at build time.
        // Returns code/hint contributions for that specific bean.
        // Spring Data generates the concrete repository implementation here.
        return ...; // contributes generated source + reflection hints
    }
}

Layer 4 — Tracing agent (fallback for unsupported libraries)

If a library has no entry in the reachability metadata repo and ships no hints, run the GraalVM tracing agent against a real JVM run. It records every reflective access, dynamic proxy creation, and resource load automatically. 

# Run the app (or tests) with the agent — exercise ALL code paths you care about.
# Use config-merge-dir (not config-output-dir) to accumulate across multiple runs.

java -agentlib:native-image-agent=config-merge-dir=\
src/main/resources/META-INF/native-image \
     -jar app.jar

# Re-run with additional scenarios to cover more code paths:
java -agentlib:native-image-agent=config-merge-dir=\
src/main/resources/META-INF/native-image \
     -jar app.jar --scenario=checkout-flow

# native-image (and Spring's build) picks up the generated files automatically.
mvn -Pnative native:compile

Layer 5 — Manual annotation hints (your own code)

For DTO classes that a library will reflect on (Jackson, ModelMapper, etc.), annotate them directly rather than writing JSON files: 

// Register a DTO for reflection (all public fields, constructors, methods)
@RegisterReflectionForBinding(UserDto.class)
@Configuration
public class NativeConfig {

    // For a whole package:
    @Bean
    public RuntimeHintsRegistrar myHints() {
        return (hints, classLoader) -> {
            hints.reflection()
                .registerType(LegacyParser.class,
                    MemberCategory.DECLARED_FIELDS,
                    MemberCategory.INVOKE_DECLARED_METHODS,
                    MemberCategory.INVOKE_DECLARED_CONSTRUCTORS);
            hints.resources()
                .registerPattern("legacy-mappings/*.xml");
        };
    }
}

12. What still breaks — and fixes

Some patterns cannot be made to work in native image regardless of hints, because they fundamentally require generating or loading new code at runtime.

PatternWhy it breaksFix / workaround
Runtime CGLib subclassing (e.g. arbitrary CGLib usage outside Spring AOP) Subclass doesn't exist at build time — can't be in the binary Spring AOT generates CGLib subclasses for @Configuration and @Transactional at build time automatically. For arbitrary CGLib use outside Spring, you must refactor.
Dynamic class loading (URLClassLoader, plugin systems) Closed-world: all classes in the binary are fixed at build time No native fix — deploy that module as a JVM service, or redesign as compile-time extension points
Scripting engines (Groovy scripts, OGNL, SpEL at runtime) Scripts compile new classes at runtime Pre-compile scripts to a fixed set; or exclude from native profile and run on JVM
Reflection on com.sun.* / JDK internals Strong encapsulation in native is stricter than --add-opens on the JVM Replace with public API; or add -H:AdditionalSecurityProviders / --add-opens equivalent in native-image args
Java serialization on unregistered classes Serialization reads field names by reflection — not found without registration Add to serialization-config.json or use hints.serialization().registerType(MyClass.class); prefer non-Java serialization (JSON, Protobuf) for new code
JPA lazy loading via Hibernate bytecode enhancement Hibernate enhances entity bytecode at class-load time Enable Hibernate's build-time bytecode enhancement (Maven/Gradle plugin); Spring Boot 3.x auto-configures this for native
Old XML Spring config (applicationContext.xml) XML parsing loads classes by string name at runtime — invisible to AOT Migrate to @Configuration Java config; or register all referenced classes in reflect-config.json via the tracing agent
Class.forName() with a runtime-computed name Class name only known at runtime — not reachable from static analysis Enumerate all possible names and register them; or use a fixed switch on known types

Practical debugging checklist

  1. Check oracle/graalvm-reachability-metadata — is the library listed? Are you on the required version?
  2. Check the library's own docs for a "GraalVM", "native image", or "AOT" section.
  3. Run mvn spring-boot:process-aot alone — does it fail? That points to a Spring-level problem (missing hints, broken condition).
  4. Read target/spring-aot/main/sources/ — look at the generated bean definition for the failing bean.
  5. Run the tracing agent against the integration test suite to capture all library accesses.
  6. Add @RegisterReflectionForBinding or a RuntimeHintsRegistrar @Bean for remaining gaps.
  7. If the library is fundamentally incompatible — deploy two profiles: native for the main app, a separate JVM service for the incompatible piece.

13. Profile-guided optimisation (PGO)

By default, Native Image compiles without knowledge of which code paths are hot at runtime — all methods get the same treatment. PGO adds a profiling step: you run a special instrumented binary that records execution profiles, then feed those profiles back into a second native-image build that uses them to make better inlining and optimisation decisions. 

# Step 1 — build an instrumented binary (Oracle GraalVM / GraalVM EE only)
native-image --pgo-instrument -jar app.jar -o app-instrumented

# Step 2 — run with realistic workload to collect profiles
./app-instrumented <typical-traffic-scenario>
# Produces: default.iprof

# Step 3 — build the final optimised binary
native-image --pgo=default.iprof -jar app.jar -o app

# Result: throughput typically reaches 80–95% of JVM peak
# (vs 65–75% for a non-PGO native image)
PGO is available in Oracle GraalVM (formerly Enterprise Edition, now free). GraalVM CE and Mandrel do not support PGO.

14. GraalVM Native Image vs JDK AOT Cache

These are often confused because both use the term "AOT", but they solve completely different problems at different layers of the stack.

Dimension GraalVM Native Image JDK AOT Cache (Project Leyden)
What it produces A standalone native binary (./app) A .aot cache file; still runs on the JVM
JVM at runtime No JVM required — binary runs natively Full JVM required — JVM loads the cache
Startup improvement ~10–50 ms (vs 1–5 s cold JVM) 40–60% faster JVM start (e.g. 5 s → 2.5 s)
Peak throughput 65–85% of JVM (without PGO); ~90–95% with PGO Same as JVM — JIT still runs fully at runtime
Memory footprint 50–80% less than a JVM app Same as JVM app (cache is disk, not RAM)
Closed-world assumption Yes — all classes must be known at build time No — dynamic class loading, runtime bytecode still work
Reflection Needs config files or tracing agent Works automatically — no changes needed
Dynamic proxies Needs proxy-config.json Works automatically
Migration effort Potentially high (reflection config, library compat) Zero — two JVM flags, same .jar
Who makes it GraalVM / Oracle (separate distribution) Standard JDK 24+, stable in 25
Distribution size Small self-contained binary (~5–50 MB) Same JAR + .aot cache file (~50–200 MB)
Container image size ~20–80 MB (FROM scratch possible) ~200–600 MB (needs full JRE/JDK)
GC Serial GC by default (fast), G1 opt-in (Oracle only) Any JVM GC (G1, ZGC, Shenandoah, Serial)
Best for Serverless, CLI tools, microservices needing <50 ms start Any existing JVM app; free startup win with no code changes

Side-by-side startup demo

## Same Spring Boot app, three configurations:

# 1. Plain JVM (cold)
time java -jar app.jar
# real  0m4.921s

# 2. JVM + AOT Cache (JDK 25 / Project Leyden)
java -XX:AOTCacheOutput=app.aot -jar app.jar     # one-time training run
time java -XX:AOTCache=app.aot -jar app.jar
# real  0m2.437s     ← ~50% faster, same jar, no code changes

# 3. GraalVM Native Image
native-image -jar app.jar -o app-native
time ./app-native
# real  0m0.082s     ← 60x faster than cold JVM, no JVM needed

Existing JVM service; want faster restart JDK AOT Cache Zero migration cost, works with everything
AWS Lambda / Google Cloud Functions GraalVM Native Image Billed per millisecond; cold-start latency is money
CLI tool or developer toolchain binary GraalVM Native Image Single binary, instant start, no JVM to install
Long-running REST API / batch job JVM (plain or + AOT Cache) JIT wins on sustained throughput; full Java features
Microservice in a container, must stay below 100 ms start GraalVM Native Image Tiny image, instant start, lower RSS per replica
App uses heavy reflection (legacy Spring XML, etc.) JDK AOT Cache first Native image config overhead may not be worth it
Quarkus / Micronaut app GraalVM Native Image Frameworks are designed for it; metadata bundled
They are not mutually exclusive. You can ship one JAR and deploy it three ways: cold JVM for local dev, JVM + AOT Cache for staging/high-throughput production, and a native image for the serverless variant — all from the same source.

16. Gotchas & limitations

IssueDetailFix
Reflection not found ClassNotFoundException or missing method at runtime Run tracing agent; add reflect-config.json
Class initialisation order Static initialiser runs at build time, but code assumes runtime values (e.g. current time) Use --initialize-at-run-time=com.example.MyClass
--no-fallback vs fallback image By default, if native-image fails analysis it creates a "fallback" that wraps a JVM. Pass --no-fallback to fail instead. Always use --no-fallback in CI to catch problems early
No JIT at runtime Tight loops that the JIT would specialise stay at the AOT-compiled level Use PGO (Oracle GraalVM) to recover throughput
Build time & RAM Native image build needs 4–8 GB RAM and 30–120 s Run in CI; use -Ob (quick build mode) for local dev
Cross-compilation By default, native-image produces a binary for the build machine's OS/arch Use Docker multi-stage builds to produce Linux binaries from macOS; or GraalVM's static image feature
Thread.sleep, finalisers, agent attach Some JVM features simply don't exist in native (finalisers, dynamic agents, JMX) Remove or replace with native-compatible alternatives
Security providers Dynamically loaded security providers (e.g. BouncyCastle via reflection) need config Register via reflect-config.json or the provider's native-image guide

17. Cheat sheet

Essential native-image flags

# Basic
native-image -jar app.jar -o myapp           # build from JAR
native-image --no-fallback -jar app.jar      # fail if analysis is incomplete

# Optimisation
native-image -O2 -jar app.jar                # optimise (default is -O2 for release)
native-image -Ob -jar app.jar                # quick build (faster, less optimised — dev mode)
native-image -march=native -jar app.jar      # target build machine's CPU ISA

# Reflection / resources
native-image -H:ReflectionConfigurationFiles=reflect-config.json -jar app.jar
native-image -H:ResourceConfigurationFiles=resource-config.json  -jar app.jar

# Static binary (Linux only, needs musl libc)
native-image --static --libc=musl -jar app.jar   # truly zero dependency binary

# PGO (Oracle GraalVM)
native-image --pgo-instrument -jar app.jar   # build instrumented binary
./app-instrumented                           # run to collect profiles
native-image --pgo=default.iprof -jar app.jar  # build optimised binary

# Debugging
native-image -g -jar app.jar                 # include debug symbols
native-image -H:+PrintAnalysisCallTree -jar app.jar  # see reachability analysis

Useful system properties at runtime

// Detect whether running as native image or on JVM
boolean isNative =
    System.getProperty("org.graalvm.nativeimage.imagecode") != null;

// Values: "buildtime" (during native-image build), "runtime" (native binary running)
String imageCode =
    System.getProperty("org.graalvm.nativeimage.imagecode", "jvm");
