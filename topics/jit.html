JIT Compilation JVM internals

The Just-In-Time (JIT) compiler is the reason Java can match C++ in long-running throughput despite shipping bytecode. It watches your program as it runs, finds the hot spots, and compiles them to native machine code on the fly — with optimisations a static compiler could never apply because it doesn't know the real call patterns at compile time.

10–100×faster than pure interpretation
10,000default invocation threshold (C2)
C1 + C2two compilers, tiered
inliningsingle biggest win
deoptJIT can always bail out safely
The problem it solves Java ships bytecode — a platform-neutral instruction set that any JVM can run. Pure interpretation of bytecode is 10–50× slower than native code. A static ahead-of-time compiler (like javac) can't see which code paths are actually hot at runtime. JIT bridges the gap: start fast by interpreting, profile the real execution, and compile only the hot paths — applying runtime-specific optimisations that make the result faster than what a static compiler can produce.

1 · What JIT actually does — the easy version

Imagine a restaurant kitchen with two modes:

Analogy. When you first open the restaurant, the chef reads each recipe card line-by-line and cooks as they read (interpretation). After hundreds of burger orders, the chef has the burger recipe memorised and can cook it from muscle memory without reading the card (JIT compilation). The first burger is slower because the chef was reading; all subsequent burgers are much faster. That's exactly what the JVM does with your methods.

More precisely:

  1. The JVM starts by interpreting bytecode — slow but requires zero setup time.
  2. It counts how many times each method is called.
  3. When a method crosses a threshold (~10,000 calls by default), the JIT compiler translates it to native machine code and caches it.
  4. Future calls go directly to the native code — no bytecode reading, no interpretation overhead.
  5. If the JIT's assumptions break (e.g. a new subclass appears), it deoptimises and falls back to the interpreter safely.

3 · Tiered compilation: C1 → C2

Java 8+ uses tiered compilation by default — two separate JIT compilers, each used at different points in a method's lifetime.

C1 — client compiler (fast & light)
// C1 compiles this quickly and starts running faster code soon
// Optimisations: simple inlining, register allocation, null-check elimination
// Goal: reduce interpretation overhead quickly — even if the code isn't perfect yet
// Used during: warm-up, short-lived CLIs, anything run < ~10k times
C2 — server compiler (slow & aggressive)
// C2 takes longer to compile but produces much better native code
// Optimisations: deep inlining, escape analysis, loop unrolling,
//   speculative devirtualization, dead code elimination, vectorization
// Goal: maximum throughput for code that runs millions of times
// Used for: tight loops, hot service paths, anything called > ~10k times
Rule of thumb: JIT warm-up takes a few seconds on a typical JVM. Benchmarks that measure cold-start time are measuring interpreter speed, not JIT speed. Always warm up before benchmarking (§15).

See which tier a method is on (flag)

// Run with: java -XX:+PrintCompilation MyApp
// Output columns: timestamp  compile-id  flags  tier  class::method  size
//
//    337  114       3       java.lang.String::hashCode (67 bytes)   ← tier 3, C1
//   1203  115 %     4       com.example.HotLoop::run @ 12 (88 bytes) ← tier 4, C2 (% = OSR)
//
// Flags:  %  on-stack replacement (OSR, see §10)
//         !  method has exception handlers
//         s  method is synchronized
//         b  blocking compilation (uncommon)

4 · Profiling — how JIT finds hot code

While the interpreter runs, the JVM collects three types of profiling data about every method:

Profile dataWhat it tracksUsed for
Invocation counterHow many times the method was calledTrigger C1/C2 compilation
Back-edge counterHow many times a loop re-entered its bodyTrigger OSR for hot loops
Type profileWhat concrete types appear at call sites and castsDevirtualization, inlining
Branch profileWhich branch of an if/switch was taken, and how oftenDead code elimination, branch layout
Call-site profileWhich method was called at each virtual dispatch siteMonomorphic / bimorphic inlining
// example: branch profile in action
void process(Object o) {
    if (o instanceof String s) {   // profiler records: "always String here (99.9%)"
        doString(s);
    } else {
        doOther(o);                // profiler: "almost never taken"
    }
}
// C2 will:
//   1. inline doString() directly into process()
//   2. mark the else branch as "uncommon trap" — if it ever fires, deoptimise
//   3. eliminate the else code from the hot path entirely
Threshold tuning. The default C2 threshold is 10,000 invocations (-XX:CompileThreshold). Lowering it compiles sooner but with less profile data — often worse code. Raising it gathers more data but delays native speed. Leave it at the default unless you have measured evidence that it's wrong.

5 · Inlining — the biggest single win

Inlining replaces a call to a method with a copy of the method's body inside the caller. This eliminates the call overhead (stack frame setup, argument passing, return), but more importantly it unlocks all the other optimisations that cross method boundaries.

Before inlining — two method calls at runtime
int getLength(String s) { return s.length(); }  // tiny method

int totalLen = 0;
for (String s : list) {
    totalLen += getLength(s);   // call + stack frame + return on every iteration
}
// JVM must: push args, create stack frame, execute body, pop frame, return — every loop
After inlining — the body is copied in
// JIT effectively transforms the loop into:
int totalLen = 0;
for (String s : list) {
    totalLen += s.length();   // no call overhead — body is right here
}
// Further: s.length() is a native field access, so this becomes a tight counter loop
// Further still: loop body may be vectorized (SIMD) or unrolled

Inlining limits — when it stops

LimitDefaultFlag
Max inline size (trivial methods always inlined)35 bytes of bytecode-XX:MaxInlineSize
Max inline size (hot methods)325 bytes-XX:FreqInlineSize
Max inline depth9 levels-XX:MaxInlineLevel
// See what the JIT inlined (add to JVM args):
// -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining
//
// Output:
//   @ 12  com.example.Foo::bar (12 bytes)   inline (hot)
//   @ 24  com.example.Foo::baz (400 bytes)  too large to inline
//   @ 36  java.util.ArrayList::size (6 bytes) inline (trivial)
Why large methods hurt performance: A method over 325 bytes (bytecode) won't be inlined, even if it's called millions of times. Keep hot methods small and focused — not because of code style, but because it enables inlining, which enables all the other optimisations.

Inlining virtual calls — the trick

Virtual method calls look un-inlineable — you don't know which implementation to copy in. JIT uses the type profile to cheat:

interface Shape { double area(); }
class Circle  implements Shape { public double area() { return Math.PI * r * r; } }
class Square  implements Shape { public double area() { return side * side; } }

for (Shape s : shapes) {
    total += s.area();   // virtual call — could be Circle or Square
}

// If the profiler saw 99.9% Circle here:
// JIT emits:
//   if (s.getClass() == Circle.class) {
//       total += /* inlined Circle.area() body */;
//   } else {
//       total += s.area();   // rare slow path, or deopt trap
//   }
// → near-static call performance, with a safety net

6 · Escape analysis & stack allocation

Normally every new allocates on the heap, which the GC must eventually collect. Escape analysis proves whether an object can ever "escape" the method that created it. If it can't, the JIT has two options:

TechniqueWhat happensBenefit
Stack allocationObject lives on the stack, freed automatically when method returnsZero GC pressure
Scalar replacementObject fields are held in CPU registers / local variables — no object at allNo memory allocation, no GC
Lock elisionSynchronized on an object only one thread ever touches — lock removedNo synchronisation cost
Code you write — looks like a heap allocation
double computeDistance(double x1, double y1, double x2, double y2) {
    Point p1 = new Point(x1, y1);   // ← heap allocation?
    Point p2 = new Point(x2, y2);   // ← heap allocation?
    return p1.distanceTo(p2);
    // p1 and p2 never leave this method — they don't escape
}
What JIT actually executes (scalar replacement)
double computeDistance(double x1, double y1, double x2, double y2) {
    // Point objects eliminated entirely — fields kept in registers:
    double dx = x2 - x1;
    double dy = y2 - y1;
    return Math.sqrt(dx*dx + dy*dy);
    // Zero heap allocations. Zero GC. Just floating-point math.
}
// Verify escape analysis is on (it is by default):
// -XX:+DoEscapeAnalysis  (default: true)

// Lock elision example:
void addItem(String item) {
    List<String> local = new ArrayList<>();  // list doesn't escape
    synchronized (local) {                    // ← this lock is elided entirely
        local.add(item);
    }
    process(local);  // still local to this call — no escape
}
// After JIT: synchronized block is a no-op, lock acquire/release removed
What breaks escape analysis. If you store the object in a field, return it, pass it to another thread, or pass it to a method the JIT can't inline — the object escapes and must stay on the heap. Keep objects local to help the JIT prove non-escape.

7 · Devirtualization & speculative optimisation

Java's polymorphism means most method calls are virtual — the JVM must look up which implementation to call at runtime. JIT uses profiling to make educated guesses and hard-code the most likely target.

Three levels of call-site optimisation

Pattern seenOptimisationResult
Only one concrete type seen (monomorphic)Inline the single implementation, guard type checkNear-static performance
Two concrete types seen (bimorphic)Two inlined branches, pick by typeGood performance
Three or more types (megamorphic)No inlining — use vtable dispatchFull virtual overhead
// monomorphic → JIT inlines (fast)
List<String> list = new ArrayList<>();   // always ArrayList
list.add("x");   // JIT knows: always ArrayList.add() → inlines it

// megamorphic → JIT can't inline (slower)
List<String> list = getList();  // could return ArrayList, LinkedList, CopyOnWriteArrayList...
list.add("x");   // JIT gives up inlining — uses vtable lookup

Speculative optimisation + deoptimisation guard

// JIT emits something like this for a monomorphic call site:
if (obj.getClass() != ArrayList.class) {
    // uncommon trap — if this fires, deoptimise back to interpreter
    uncommon_trap();
}
// inlined ArrayList.add() body here (fast path, no vtable)

// If a new type appears later (e.g. LinkedList is added to the same variable):
// → the guard fires → deoptimise → recompile with bimorphic or megamorphic dispatch

8 · Loop optimisations

Loops are where most CPU time is spent, so C2 applies several transformations to them.

8.1 · Loop unrolling — reduce branch overhead

// What you write:
for (int i = 0; i < 1000; i++) {
    sum += arr[i];
}

// What C2 may emit (4× unrolled — simplified):
for (int i = 0; i < 1000; i += 4) {
    sum += arr[i];
    sum += arr[i+1];
    sum += arr[i+2];
    sum += arr[i+3];
}
// Benefit: 4× fewer loop-back branches, better CPU pipeline utilisation

8.2 · Vectorisation (SIMD) — one instruction, multiple data

// What you write:
for (int i = 0; i < n; i++) {
    result[i] = a[i] + b[i];
}

// What C2 may emit (using AVX2 — 8 ints at once):
// VPADDD ymm0, [a+i*4], [b+i*4]   ← adds 8 integers in a single CPU instruction
// Benefit: 4–8× throughput for numeric loops (depends on CPU and array size)
// Requires: no aliasing, no exceptions, simple loop body

8.3 · Range-check elimination

// Every array access arr[i] normally generates a bounds check:
//   if (i < 0 || i >= arr.length) throw ArrayIndexOutOfBoundsException;

// C2 proves that inside for(int i=0; i<arr.length; i++) the index is always valid:
// → removes ALL bounds checks inside the loop
// → the check only happens once at the loop entry guard

// This is why iterating a plain array is faster than you might expect

8.4 · Loop invariant hoisting

// What you write:
for (int i = 0; i < list.size(); i++) {   // list.size() called every iteration
    process(list.get(i));
}

// What C2 does (hoists the invariant):
int size = list.size();                    // computed once, before the loop
for (int i = 0; i < size; i++) {
    process(list.get(i));
}
// Benefit: one less method call per iteration (even though size() is trivial)

9 · Deoptimisation — when JIT bails out

JIT compiles code based on assumptions derived from profiling. When those assumptions are violated at runtime, the JVM performs a deoptimisation: it throws away the compiled code for that method and falls back to the interpreter, then recompiles later with updated information.

Common deoptimisation triggers

TriggerExample
New subclass loadedJIT inlined Animal.speak() assuming only Dog; then Cat is loaded
Uncommon trap firesA branch the profiler said was "never taken" actually executes
Class re-initialisationA static field the JIT treated as constant is changed via reflection
Bytecode patchedA Java agent or debugger modifies bytecode at runtime
Null check failed after elisionJIT removed a null check; a null appears
// Deoptimisation is safe — the JVM can always reconstruct the interpreter state
// from the compiled frame at any safepoint.

// You can observe deoptimisations:
// java -XX:+TraceDeoptimization MyApp
// Output:
//   Uncommon trap occurred in com.example.Foo.bar() @ bci 12 reason=class_check action=reinterpret

// Frequent deoptimisations are a performance red flag — they cause:
//   1. Repeated recompilation
//   2. Interpreter overhead during recompile window
//   3. Possible "deoptimisation storms" in heavily polymorphic code
How to trigger a deoptimisation on purpose (for learning): Call a method 20,000 times with one type (so C2 inlines it), then call it with a different type. The guard fires, deoptimisation occurs, and you can observe it with -XX:+TraceDeoptimization.

10 · On-Stack Replacement (OSR)

Normal JIT compilation takes effect on the next call to the compiled method. But what if you have one enormous long-running loop that runs for minutes? You'd be stuck in the interpreter for the whole duration. OSR solves this.

// OSR is visible in -XX:+PrintCompilation output as the % flag:
//   1203  115 %     4     com.example.Crunch::run @ 12 (88 bytes)
//         ↑ %                                     ↑ bytecode index of OSR entry point
//   This means: OSR compilation at tier 4, entering the loop at bytecode 12

// OSR is the reason a tight benchmark loop "speeds up" after a second or two:
long sum = 0;
for (int i = 0; i < 100_000_000; i++) {   // back-edge counter fires ~10k iterations in
    sum += i;                               // JIT compiles via OSR, rest of loop is native
}
System.out.println(sum);

11 · Code cache

Compiled native methods are stored in a fixed-size region of memory called the code cache. If it fills up, the JVM stops JIT-compiling new methods — everything runs in the interpreter or at the last tier it reached.

// Default sizes (64-bit JVM, Java 11+)
// -XX:ReservedCodeCacheSize=240m   (total size reserved)
// -XX:InitialCodeCacheSize=2496k   (initial committed)

// Warning you'll see if it fills:
// "CodeCache is full. Compiler has been disabled."
// "Try increasing the code cache size using -XX:ReservedCodeCacheSize="

// Check code cache usage at runtime (JMX / JConsole → Memory → Code Cache)
// or: jcmd <pid> Compiler.codecache

// Three segmented code heaps (Java 9+ with tiered compilation):
// NonNMethods:   JVM internal / glue code
// NonProfiled:   tier 2/3 C1 code (has profile counters removed)
// Profiled:      tier 3 C1 code with profiling still active

// If only Profiled fills: methods get stuck at tier 3, never promoted to C2
// Solution: -XX:ReservedCodeCacheSize=512m   (or profile with JFR to find waste)

13 · AOT vs JIT — tradeoffs

Ahead-Of-Time (AOT) compilation (e.g. GraalVM native-image, or the AOT cache added incrementally from Java 17) compiles bytecode to native code before the program runs. This eliminates warm-up but loses runtime adaptability.

JIT (default HotSpot)AOT (native-image)
Startup timeSlow (seconds to warm up)Instant (milliseconds)
Peak throughputHighest — adapts to real dataLower — compiled without runtime data
Memory footprintLarger (JVM + code cache)Smaller (no JVM overhead)
Dynamic class loadingFull supportLimited — closed-world assumption
Reflection / proxiesFull supportRequires config or Reachability Metadata
Best forLong-running servers, batch, anything running > 30sCLIs, serverless FaaS, containers needing fast startup
// JIT warm-up profile (typical web service):
//   t=0s   → cold interpreter  (10–50× slower than peak)
//   t=5s   → C1 compiled       (~3–5× slower than peak)
//   t=30s  → C2 compiled       (at or near peak throughput)
//   t=∞    → steady state

// AOT profile (GraalVM native-image):
//   t=0ms  → already at peak   (but peak is lower than JIT peak)
//   t=∞    → same steady state
Java 24+ ships an AOT cache (java -XX:AOTCache=app.aot) that stores C2-compiled code from a training run and replays it in future JVM starts — getting near-AOT startup without the closed-world constraints of native-image. See the AOT Cache deep dive.

15 · Writing JIT-friendly code

You don't need to think about JIT for most code. These rules help when performance matters.

15.1 · Keep hot methods small

// Bad: one giant method — won't be inlined anywhere
void processOrder(Order o) {
    // 400+ lines of validation, calculation, persistence, logging
}

// Good: small focused methods — each can be inlined by callers
void processOrder(Order o) {
    validate(o);        // 20 lines → inlineable
    calculate(o);       // 30 lines → inlineable
    persist(o);         // 25 lines → inlineable
    audit(o);           // 15 lines → inlineable
}

15.2 · Prefer monomorphic call sites

// Bad: megamorphic — JIT can't inline
List<?> list = getAnyList();   // ArrayList, LinkedList, or CopyOnWriteArrayList?
list.size();                    // vtable dispatch, no inlining

// Good: known type — JIT inlines aggressively
ArrayList<String> list = new ArrayList<>();
list.size();   // always ArrayList → inlined to a field read

15.3 · Don't use reflection in hot loops

// Bad: reflection bypasses JIT inlining
Method m = clazz.getMethod("getValue");
for (Item item : items) {
    Object val = m.invoke(item);   // opaque to JIT — can't inline, can't optimise
}

// Good: use a direct call or a functional interface
Function<Item, Object> getter = Item::getValue;   // JIT can inline this
for (Item item : items) {
    Object val = getter.apply(item);
}

15.4 · Warm up before benchmarking

// Use JMH (Java Microbenchmark Harness) — handles warm-up automatically
@Benchmark
@Warmup(iterations = 5, time = 1)    // 5 × 1s warm-up rounds
@Measurement(iterations = 10, time = 1)
public int measure() {
    return hotMethod();
}

// Without JMH, warm up manually:
// 1. Run the method 20,000+ times before recording timing
// 2. Never trust the first N seconds of latency numbers
for (int i = 0; i < 50_000; i++) hotMethod();   // warm-up
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) hotMethod(); // benchmark
System.out.println((System.nanoTime() - start) / 1_000_000 + " ms");

15.5 · Avoid object allocation in tight loops (when profiling says so)

// Bad: allocates a new StringBuilder every iteration
List<String> result = new ArrayList<>();
for (String s : lines) {
    result.add(new StringBuilder(s).reverse().toString());   // alloc + GC pressure
}

// Better: reuse (but check if escape analysis already handles it before optimising)
StringBuilder sb = new StringBuilder();
for (String s : lines) {
    sb.setLength(0);
    result.add(sb.append(s).reverse().toString());
}
// Note: always profile first — escape analysis may already elide the allocation

15.6 · Avoid synchronization on local (per-thread) objects

// Don't do this: JIT may not prove the lock isn't shared if the object leaks
synchronized (new Object()) { ... }   // JIT elides this — it's on a new object

// Lock elision only works when the object genuinely doesn't escape
// If you pass it to another method the JIT can't inline, the lock stays

Cheat sheet

JIT compilation in one glance

ConceptWhat to remember

JIT-friendly code checklist

  • Keep hot methods under 35 bytes of bytecode (check with -XX:+PrintInlining).
  • Prefer concrete types over interfaces at hot call sites → monomorphic dispatch → inlining.
  • Avoid reflection in hot loops — it blocks inlining.
  • Let objects stay local to methods — escape analysis eliminates heap allocations.
  • Trust the JIT before manually "optimising" — profile first with JFR or async-profiler.
  • Never benchmark without warm-up. Use JMH.
